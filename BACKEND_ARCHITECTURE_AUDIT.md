# Backend Architecture Audit - Class Attendance System

## Executive Summary

This document provides a comprehensive audit of the backend architecture, examining the database schema, API structure, business logic flow, security mechanisms, and how all components connect together.

---

## 1. Technology Stack

### Core Dependencies
- **Runtime**: Node.js with Express 5.2.1
- **Database**: PostgreSQL with Prisma ORM 7.8.0
- **Authentication**: JWT (jsonwebtoken) with bcryptjs for password hashing
- **Security**: express-rate-limit, Zod for validation
- **File Processing**: multer, xlsx, pdf-parse, docxtemplater
- **QR Code**: qrcode library
- **Others**: cookie-parser, cors, dotenv

### Architecture Pattern
- **MVC Pattern**: Controllers, Routes, Middleware separation
- **RESTful API**: Standard HTTP methods (GET, POST, PATCH, DELETE)
- **Middleware Chain**: Rate limiting → Authentication → Authorization → Business Logic

## 2. Database Schema Analysis

### Core Entities

#### **User** (Multi-role system)
```prisma
- Roles: SUPERADMIN, ADMIN, REP, LECTURER
- Authentication: username/password (bcrypt hashed)
- Status: isActive flag for account management
- Relations: 
  - One-to-One with Class (as rep)
  - One-to-Many with AttendanceSession (as creator/approver)
  - One-to-Many with LecturerAssignment
```

#### **Student**
```prisma
- Unique identifiers: indexNumber, email
- Security: deviceFingerprint (device binding)
- Relations: Many-to-Many with Class via ClassStudent
```

#### **Programme → Class → Course** (Hierarchical Structure)
```prisma
Programme (e.g., "BIT", "BSc CS")
  └─ Class (level + type + group + session)
      └─ Courses (via ClassCourse junction)
      └─ Students (via ClassStudent junction)
      └─ Rep (One-to-One with User)
```

**Class Naming Convention**:
```
{Programme} LEVEL {level} {type} GROUP {group} ({session})
Example: "BIT LEVEL 300 TOP-UP GROUP B (EVENING)"
```

#### **AttendanceSession** (Core Business Entity)
```prisma
- Status Flow: OPEN → CLOSED → APPROVED
- Session Types: PHYSICAL, ONLINE
- Security Features:
  - QR Code (JWT token with expiry)
  - Geofencing (latitude/longitude + radius)
  - Network SSID validation
- Lifecycle:
  1. REP creates session (status: OPEN)
  2. Students check in
  3. REP closes session (auto-marks absent students)
  4. LECTURER approves session (adds signature)
```

#### **Attendance**
```prisma
- Status: PRESENT, ABSENT, LATE
- Metadata: ipAddress, deviceInfo, locationData
- Linked to: Session + Student
```

#### **LecturerAssignment** (Course Allocation)
```prisma
- Links: Lecturer + Class + Course
- Purpose: Defines which lecturer teaches which course to which class
- Used for: Access control, report signing, notifications
```

#### **Notification**
```prisma
- Dual targeting: userId (for staff) OR studentIndex (for students)
- Types: INFO, SUCCESS, WARNING, DANGER
- Read tracking: isRead flag
```

#### **Grievance** (Student Complaints)
```prisma
- Types: ABSENCE_EXCUSE, SYSTEM_ISSUE, INTEGRITY_REPORT, GENERAL_COMPLAINT
- Status: PENDING → RESOLVED/REJECTED
- Anonymous support: Redacts studentIndex/studentName
- Evidence: File upload support
```

#### **OfficialReport** (Attendance Reports)
```prisma
- Status: PENDING_SIGNATURE → SIGNED
- Generated by: REP (using docxtemplater)
- Signed by: LECTURER
- Template: ReportTemplate (master .docx file)
```

#### **SystemSettings** (Global Configuration)
```prisma
- deptName, deptLogoUrl
- lateWindowMinutes (grace period for LATE status)
- qrExpirySeconds (QR code refresh interval)
- geofenceRadiusMeters (location tolerance)
```

```
├── /lecturer                # Lecturer assignments
├── /admin                   # SuperAdmin operations
└── /stats                   # Dashboard statistics
```

### Authentication Flow

#### 1. **Login** (`POST /api/auth/login`)
```javascript
Input: { username, password }
Process:
  1. Validate credentials (bcrypt.compare)
  2. Check isActive status
  3. Generate short-lived access token (15 min)
  4. Generate long-lived refresh token (7 days)
  5. Set refresh token in HttpOnly cookie
Output: { token, user, needsPasswordChange }
```

#### 2. **Token Refresh** (`POST /api/auth/refresh`)
```javascript
Input: refreshToken (from HttpOnly cookie)
Process:
  1. Verify refresh token
  2. Check user still active
  3. Generate new access token (15 min)
Output: { token }
```

#### 3. **Middleware Chain**
```javascript
protect → Verifies JWT → Attaches req.user
authorizeRoles(...roles) → Checks req.user.role
```

## 4. Security Architecture

### 4.1 Rate Limiting (3 Tiers)

```javascript
// Login Protection (Brute Force Prevention)
loginLimiter: 5 requests per minute per IP

// Check-in Protection (Automation Prevention)
checkInLimiter: 10 requests per minute per IP

// General API Protection
apiLimiter: 100 requests per 15 minutes per IP
```

### 4.2 Bodyguard Middleware (Check-in Security)

**Purpose**: Multi-layer validation for student attendance marking

**Validation Layers**:

1. **Lockout Check**
   - Tracks failed attempts per indexNumber and IP
   - Threshold: 10 failures → 15-minute lockout
   - Cache: In-memory (failedAttempts, lockedKeys Maps)

2. **Input Validation** (Zod Schema)
   ```javascript
   - indexNumber: 5-15 characters
   - name: min 2 characters
   - deviceFingerprint: min 5 characters
   - sessionId OR qrCode: required
   - latitude/longitude: optional (required for PHYSICAL)
   - networkSSID: optional
   ```

3. **Student Verification**
   - Student exists in database
   - Device fingerprint binding (one device per student)
   - First check-in: binds fingerprint
   - Subsequent: validates fingerprint match

4. **Session Integrity**
   - QR Code: JWT verification + expiry check
   - Session status: Must be OPEN
   - Session cache: In-memory for performance

5. **Physical Verification** (for PHYSICAL sessions)
   - **Geofencing**: Haversine formula distance calculation
     ```javascript
     distance = getDistance(session.lat, session.lon, student.lat, student.lon)
     if (distance > geofenceRadius) → REJECT
     ```
   - **Network SSID**: Case-insensitive match

6. **Class Enrollment**
   - Verify student is enrolled in session's class
   - Check ClassStudent junction table

7. **Duplicate Prevention**
   - Check if student already checked in for this session

8. **Status Determination**
   ```javascript
   minutesElapsed = (now - session.startTime) / 60000
   status = minutesElapsed > lateWindow ? 'LATE' : 'PRESENT'
   ```

**On Success**: Attaches `req.bodyguard = { student, session, attendanceStatus }`

**On Failure**: 
- Records failure in cache
- Triggers lockout if threshold reached
- Sends security alert to REP

### 4.3 Security Cache (In-Memory)

```javascript
// Active Sessions Cache
activeSessions: Map<sessionId, sessionData>
- Purpose: Avoid DB queries for every check-in
- Lifecycle: Cached on OPEN, evicted on CLOSE

// Failed Attempts Tracking
failedAttempts: Map<key, { count, lastAttempt }>
lockedKeys: Map<key, { lockUntil }>
- Keys: indexNumber or IP address
- Threshold: 10 failures → 15-minute lockout
```

### 4.4 Password Security

```javascript
// Registration/Password Change
bcrypt.hash(password, 10) // 10 salt rounds

// Login
bcrypt.compare(plainPassword, hashedPassword)

// Default Passwords
- SuperAdmin: "admin123" (forces change on first login)
- Lecturer: "gctuLecturer123!" (bulk upload)
```

## 6. Role-Based Access Control (RBAC)

### Role Hierarchy

```
SUPERADMIN (Highest)
  ├─ Full system access
  ├─ Manage programmes, classes, courses
  ├─ Manage users (REP, LECTURER, ADMIN)

  ├─ Similar to SUPERADMIN
  └─ Cannot modify system settings

LECTURER
  ├─ View assigned classes/courses
```

## 7. Data Flow Patterns

### 7.1 Notification System

**Dual Targeting**:
```javascript
// For authenticated users (REP, LECTURER, ADMIN)
createNotificationHelper({ userId, title, message, type })

// For students (unauthenticated)
createNotificationHelper({ studentIndex, title, message, type })
```

**Trigger Points**:
- Session opened → All students
- Student checks in → Student + REP
- Session closed → REP + All lecturers
- Session approved → REP
- Grievance resolved → Student (if not anonymous)
- Low attendance warning → At-risk students

### 7.2 Caching Strategy

**Session Cache** (Performance Optimization):
```javascript
// Cache on session creation (OPEN)
cacheSession(session)

// Retrieve from cache (check-in validation)
getCachedSession(sessionId) // Falls back to DB if not cached

// Update cache (QR refresh)
updateCachedSession(sessionId, { qrCode, qrCodeExpiry })

// Evict from cache (session closed)
removeCachedSession(sessionId)
```

**Security Cache** (Brute Force Protection):
```javascript
// Record failure
recordFailure(key) // key = indexNumber or IP
  → Increment counter
  → Lock if threshold reached (10 failures)

// Check lockout
isLocked(key) → boolean

// Reset on success
resetFailures(key)
```

### 7.3 Async Notification Pattern

**Non-blocking Notifications**:
```javascript
// Controller creates attendance record
const attendance = await prisma.attendance.create(...)

// Async notification (doesn't block response)
(async () => {
  try {
    await createNotificationHelper(...)
  } catch (err) {
    console.error('Notification failed:', err)
  }
})()

// Immediate response to client
res.status(201).json({ message: 'Success', attendance })
```

## 9. Error Handling & Resilience

### 9.1 Database Connection

**Retry Mechanism**:
```javascript
connectWithRetry(attempts = 5, delay = 5000)

  - On failure: Wait 5s, retry
  - After 5 failures: Exit process
```

**Signal Handlers**:
```javascript

process.on('SIGTERM', gracefulShutdown)
process.on('unhandledRejection', gracefulShutdown)
process.on('uncaughtException', gracefulShutdown)

gracefulShutdown():
  1. Close HTTP server
  2. Disconnect Prisma
```

## 10. Key Observations & Recommendations

### ✅ Strengths

1. **Comprehensive Security**:
   - Multi-layer validation (bodyguard)
   - Rate limiting at multiple levels
   - Device fingerprinting
   - Geofencing + SSID validation

2. **Well-Structured Architecture**:
   - Clear separation of concerns (MVC)
   - Middleware chain pattern
   - Reusable helper functions

3. **Robust Data Model**:
   - Proper normalization
   - Junction tables for many-to-many
   - Cascade deletes configured

4. **Performance Optimizations**:
   - In-memory session cache
   - Async notifications (non-blocking)

5. **Resilience**:
   - Database retry mechanism
   - Graceful shutdown handlers
   - Global error handling

### ⚠️ Areas for Improvement

1. **Security Cache Persistence**:
   - **Issue**: In-memory cache lost on restart
   - **Impact**: Lockouts reset, security counters lost
   - **Recommendation**: Use Redis for persistent cache

2. **Session Cache Invalidation**:
   - **Issue**: No TTL on cached sessions
   - **Impact**: Memory leak if sessions not properly closed
   - **Recommendation**: Add TTL or periodic cleanup

3. **QR Code Security**:
   - **Issue**: QR codes stored in database (can be reused if leaked)
   - **Current**: JWT expiry provides some protection
   - **Recommendation**: Consider one-time-use tokens

4. **Device Fingerprinting**:
   - **Issue**: Client-side generated (can be spoofed)
   - **Recommendation**: Server-side fingerprinting (IP + User-Agent + headers)

5. **Notification Delivery**:
   - **Issue**: Fire-and-forget async (no retry on failure)
   - **Recommendation**: Queue-based system (Bull/BullMQ)

6. **File Upload Validation**:
   - **Issue**: No file size limits on some uploads
   - **Issue**: No MIME type validation
   - **Recommendation**: Add multer limits and file type checks

7. **Lecturer Assignment Upload**:
   - **Issue**: No transaction wrapper (partial failures possible)
   - **Recommendation**: Wrap in Prisma transaction

8. **Password Policy**:
   - **Issue**: Weak default passwords
   - **Issue**: No password complexity requirements
   - **Recommendation**: Enforce strong password policy

9. **API Versioning**:
   - **Issue**: No versioning strategy
   - **Recommendation**: Add /api/v1 prefix for future compatibility

10. **Logging**:
    - **Issue**: Console.log only (no structured logging)
    - **Recommendation**: Use Winston or Pino for production logging

11. **Environment Variables**:
    - **Issue**: Fallback to hardcoded secrets (JWT_SECRET)
    - **Recommendation**: Fail fast if critical env vars missing

12. **CORS Configuration**:
    - **Issue**: Hardcoded origins (localhost only)
    - **Recommendation**: Use environment variable for production origin

## 13. Conclusion

The backend architecture is **well-designed and comprehensive**, with strong security mechanisms, clear separation of concerns, and robust business logic. The multi-layer validation approach (especially the bodyguard middleware) demonstrates thoughtful security design.

**Key Strengths**:
- Comprehensive security (rate limiting, device binding, geofencing)
- Clean MVC architecture
- Proper database normalization
- Performance optimizations (caching)

**Priority Improvements**:
1. Persistent cache (Redis) for security counters
2. Transaction wrappers for bulk operations
3. Structured logging (Winston/Pino)
4. File upload validation (size, MIME type)
5. Environment variable validation (fail fast)

The system is **production-ready** with the recommended improvements implemented.
